## Svc Owner Workflows V2 bounded successor delta

This successor preserves the full accepted V1 design, including all singleton identities, effects, authorization fences, exact GCR commands, error classes, STOP behavior, producer lineage, and restrictions on recursion. It adds one missing producer seam for V1 §6: optional `contextPayload` on the existing transition, restricted to entering a declared gated TASK from managed INTAKE by ADVANCE/RETURN. Storage V0.3 remains sufficient: Context revisions stay immutable and append-only, while the existing Instance current-context projection is an allowed command update; no new table or migration is introduced.

Present `currentNode` is `{nodeVisitId,nodeDefinitionId,workflowStateVersion,operation?,reviewAdmission?}`; present `operation` is `{slotKey,allowedOperations,targetDefinitionVersionId?,targetDefinitionDigest?,effect}`. Optional `reviewAdmission` is present only for an admissible active REVIEW resolve node and has exactly `{version:1,status:'ADMISSIBLE',source:{workflowInstanceId,nodeVisitId,definitionVersionId},owner:{principalId,bindingId},proof:{bindingId,terminalEventId,submissionId,submissionDigest,acceptanceContractDigest}}`; every field is required when present and null/partial objects are forbidden. The Svc producer joins the REVIEW singleton, frozen policy/DefinitionVersion, actual case, exact BOUND governance relation, verified terminal Event/Submission proof, current visit/node/slot, and current enabled Owner/assignment under one authorization-consistent snapshot. It verifies the current Owner/assignee, source visit and source Definition lineage, binding and terminal-event references, and all five immutable proof values with the existing terminal-proof verifier; the owner-change fence, configured policy-actor approval and required responsibility state must also remain valid. The projection authorizes one guarded attempt but is not delivery evidence or business completion. Non-REVIEW nodes omit it; an unprovable current REVIEW fails closed or returns its declared typed STOP/UNKNOWN, never an admissible partial value. `effect` is a closed union: `{state:'NOT_STARTED'}` only after an authoritative lookup under the stable semantic key proves no claim; `{state:'PREPARED'|'STARTED'|'UNKNOWN',effectId,requestDigest?,commandId?}` with only actually stored coordinates; `{state:'SUCCEEDED',effectId,commandId,requestDigest,result,resultDigest}` with actual stored receipt/result; or `{state:'REJECTED_ZERO_FACTS',effectId,commandId,requestDigest,failure}` with actual deterministic failure receipt. Missing commandId is not zero-fact evidence. Present `stop` is `{code,responsibilityId,ownerReplacementCommandId?,nodeVisitId?,attemptId?,effectId?}` and omits unavailable values. A caller that lost a first effect response discovers the effect through `read(workflowInstanceId)`; no effectId guess or replay key is needed. `read_effect` remains available when the effectId is known. Storage failure, missing/corrupt managed relation, ambiguous receipt or unproven lineage is UNKNOWN, never NOT_STARTED.

For ordinary-create effects only, Core obtains the source CAS from exactly one same-caller existing `workflow_assistance_read.detail({assistanceCaseId})` read (`GET /internal/v1/assistance-cases/{assistanceCaseId}`, `workflow.read`), keyed by this managed relation's case. The effect envelope's `expectedSourceWorkflowStateVersion` is the actual returned `workflowStateVersion`, after Core verifies exact case ID, source `workflowInstanceId`, source `nodeVisitId`, `currentNodeVisitId`, BOUND binding and source lineage against this managed relation. Assistance resolve/escalate keeps the caller's explicit `expectedWorkflowStateVersion` unchanged in both business DTO and source CAS; the read may validate equality but never replace it.

The activation gate is the measured model-tool-reachable boundary: the actual native immutable exact allowlist exposes only the closed workflow Broker surface and prevents file/exec/HTTP/MCP escape; the active policy-generation ACK is present; a non-sensitive synthetic deny probe is observed; Broker/module/policy configuration is not model-writable; and environment readback exposes key names only, never values. This does not require OS same-UID or ACL separation and does not authorize a new native feature. A75 itself retained read/write access and does not satisfy the gate. A normal Svc JWT does NOT identify a Core turn; the Svc API still enforces its own case/visit/actor/effect predicates. Without the complete measured boundary, producer activation is blocked. No Auth-service/grant change is silently included.

## 8. Owner ABA/unsupported-stop, bounds and termination

Current Owner assignment epoch is the actual successful Owner-replacement command ID plus recipient Principal, following existing GCR review semantics; binding-row UUID alone is insufficient for A→B→A. No-op/replay replacement creates no new epoch. Stable effect identity, intake/review singleton and successful results NEVER reset across replacement.

V1 DOES NOT SUPPORT AUTOMATIC VISIT HANDOFF. In the actual Owner-replacement transaction, under the existing Domain guard, mark each affected managed responsibility OWNER_CHANGED_UNSUPPORTED and persist a deduped STOP keyed by the actual replacement command. For an INTAKE responsibility whose singleton has not yet been born, stop its existing lifetime-unique `workflow_owner_obligation_intents` row even when `managed_instance_id` and `binding_id` are absent; record actual replacement command provenance there, leave those unknown coordinates absent, and make STOPPED absorbing for V1 including A→B→A. Serialize replacement and materialization on the same Domain/Owner fence: if materialization commits first, stop the real managed relation; if replacement commits first, no managed birth or binding may commit. Old Owner immediately fails fresh effect/managed-transition authorization; managed due filtering emits no READY attempts while stopped. Do not mutate/reassign old visits, create a replacement visit/workflow, reset a successful/UNKNOWN effect or consume new budgets. Existing results remain readable to the authorized current Owner through narrow effect readback. This is an explicit durable limitation, not a claim of unattended Owner replacement. No-op/replay replacement is deduped, never treated as a new work plan. A future handoff/recovery protocol is deferred.

No new Svc admission-claim API or per-logical-operation cross-RETURN counter is added. The actual Core WAE ledger admits at most three WEC attempts per real NodeVisit, enforcing the managed limit under its existing admission lock; a higher global override cannot relax this managed cap. No pending/UNKNOWN/quiescence bypass is permitted. Svc freezes each managed RETURN edge at maxReturnsPerEdge=3 using its existing RETURN Event counter under the instance lock. Publication proves the complete ADVANCE subgraph acyclic and every nonterminal normal path reaches terminal. With `T` TASK nodes and `E_RETURN` RETURN edges, maximum admitted TASK turns are `3 * T * (1 + 3 * E_RETURN)`. This is an upper bound; it does not claim each turn runs or succeeds. Stable effects remain unique across all visits/attempts, and Owner change never resets the bound.

Actual STOP producers are existing receipts/transactions: WAE `escalateAttemptLimit` invokes the existing Svc system-execution-escalation transaction, which records one STOP against the actual managed/source instance, NodeVisit, last Attempt and execution-policy evidence; the real Svc transaction that commits the RETURN limit records `RETURN_LIMIT_REACHED` against its Event and target Visit; deterministic effect rejection stores `OPERATION_REJECTED_ZERO_FACTS` with its original failure receipt; an unresolved effect remains UNKNOWN and readback-only. Preserve existing Event cardinality and do not synthesize HUMAN_REQUIRED. STOP/UNKNOWN appears through the existing authorized current-Owner inbox/detail and the narrow managed relation; no new global feed. New input, new effect identity, handoff, or budget reset requires separate future authority.

INTAKE/REVIEW managed class is service-owned from relations, not caller Context flags. These target Definitions cannot opt into automatic intake. Their ordinary create operations must pin one exact published Version/digest whose target has neither a managed role nor auto-intake policy. All ordinary create routes reject the dedicated managed INTAKE/REVIEW Versions with `MANAGED_WORKFLOW_POLICY_REQUIRED`; only the internal policy producer may create them. A normal governed create creates a recorded DEPENDENCY leaf with `{createdInstanceId,parentEffectId,parentManagedInstanceId,caseId}` under its actual receipt. V1 leaves cannot create more workflow instances: Broker refuses their create tool and Svc guard refuses any further create effect. Their own assistance/attempt-cap request is recorded with `NESTED_ASSISTANCE_UNSUPPORTED` STOP under the parent; it cannot start another auto-intake or naked Owner execution path. This is a bounded mechanism-specific stop and does not change unrelated ordinary workflows. The mechanism graph remains one source case → one INTAKE GCR child → finite dependency leaves, plus at most one nonchild REVIEW per exact child terminal Event.

Source cancel/archive/VOID or superseding request retires pending responsibilities and stops new effects. Existing in-flight managed writes fail fresh guards. Cancel nonterminal managed intake/review workflows through separate properly authorized/receipted existing cancel-closure commands, not direct deletion/history rewriting or a multi-Event ordinary command; close their activations. The expected-review-resolution cleanup exception above remains valid because it adds no new source effects. Independently created ordinary business instances are NOT silently canceled/deleted without separate authority; preserve their facts and report any remaining responsibility explicitly. No manual process kills/resend/node advances are part of this mechanism.

## 9. Required counterexamples/acceptance matrix

1. Request commit then reconciler crash/duplicate/restart: one recoverable intake responsibility, exactly one child/binding; source request remains its own command; no3-Event receipt.
2. Terminal commit then review-producer crash/restart/recipient changes: one review singleton; one separate birth command; naked chat and workflow never dual-execute.
3. Create succeeds but response/submission lost: same effect returns original result after readback; attempt/newturn/RETURN/newOwner cannot duplicate supplier or change effect ID.
4. Lost commit result/no coordinates: UNKNOWN not zero-facts; no new key, child, replacement or auto compensation. Actual known-zero-fact failure remains distinct and bounded.
5. Required action omitted or model completed: current TASK/terminal guard refuses progress without its actual effect facts; normal WEC continuation remains bounded.
6. Same effect with changed body/undeclared slot/key/version/hash: no second write. Input correction is not supported automatically in V1; preserve the zero-fact rejection and stop. Success is never reset.
7. Supplier UUID absent at child birth: legal prerequisite-free intake entry, no fake UUID; later gated node UNKNOWN/WAITING receives zero attempts; real receipt binding+terminal proof becomes READY through normal query-before-LIMIT path.
8. Wrong producer slot, foreign Domain/version/transition, fake Context IDs or unrelated terminal proof: fail closed, no create/dispatch/acceptance.
9. Owner A→B→A/no-op/replay; replacement races terminal/create/resolve: exact actual assignment, one OWNER_CHANGED_UNSUPPORTED stop per command, no handoff/reset/old-Owner write, no time-based quiescence claim.
10. Source resolves through this review slot before review self-completion: review can finish using exact original receipt; unrelated resolution/voiding retires it instead.
11. Governed native turn calls plain workflow_execute.create_instance/transition to bypass fixed operation: refuse/guard using actual runtime provenance; no prompt-only enforcement. No caller may mint workflow context.
12. Parent termination/failure/cap: retire/close managed activations with real receipts, durable STOP, no nested auto-intake/review loops, no invented HUMAN_REQUIRED or silent ordinary-instance cleanup.

## 13. Preserved decision and limits

The only selected execution plan is the exact published intake Workflow and separate review Workflow, using the existing graph and execution mechanisms. Actual WAE's per-Visit attempt cap, Svc RETURN's per-edge event cap, and finite managed ADVANCE DAG provide the bounded continuation; effects remain stable across all admitted visits. A dependency created by a governed operation is a pinned leaf, and nested Assistance is durably stopped without re-entering an auto-intake path. Do not add a second flat catalog/template/resultOf/materializer/completeness evaluator or a Core case-phase executor. A completed delivery or normal Owner turn is not business satisfaction. Stable Owner V1 has a defined receipt-backed path; Owner replacement is explicitly a durable unsupported-stop in V1, not a falsely promised handoff. Any later expansion is a separate accepted change.

## 14. Alternatives and disposition

- A flat obligation catalog, custom template/materializer, `resultOf` resolver, or second Core phase engine would create a competing workflow language; use the exact published intake/review graph and existing WAE/WEC instead.
- A new model-facing effect write tool or generic Svc token authority would duplicate the existing write surface and weaken provenance; reuse existing model-visible write entries with the trusted local wrapper and Svc guard.
- Automatic handoff, cross-RETURN attempt ledger, new retries after UNKNOWN/rejection, or dynamic Version selection would reset identity or create unbounded work; V1 uses actual WAE/RETURN producers, pinned target versions, readback-only UNKNOWN, and `OWNER_CHANGED_UNSUPPORTED` stop.
- Recursive auto-intake/review or ordinary-created managed targets would re-enter the mechanism; dedicated roles are internally created, effect dependencies are leaves, and nested assistance is a typed stop.
